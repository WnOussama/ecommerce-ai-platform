# ChatTurnOrchestrator is a pure decision engine, not a side-effecting one

`chat.py`'s `send_message` inlines intent classification, prompt assembly, and rules/coupon orchestration alongside its own DB writes (`_log_user_message`, `_log_assistant_message`, `_generate_coupon_from_rule`), with zero seam between "decide what to say" and "persist what happened." We're extracting the deciding half into `ChatTurnOrchestrator`. Its interface returns a plain result describing the reply, the matched rule, and the coupon to generate (if any) — it does not write to Postgres itself; the endpoint executes those writes after calling it.

This is a deliberate asymmetry with the admin agent (`app/domain/services/admin/agent_v2.py`), whose action handlers *do* write directly from inside their own "decide" logic — a future reader comparing the two will reasonably ask why chat doesn't. The reason: a Turn's DB session and idempotency handling are transport/persistence concerns the orchestrator shouldn't need to know about to be tested, and mixing them in was exactly what made `chat.py` shallow in the first place (see the architecture review, 13 Sep 2026, Candidate 1). The admin agent's shape wasn't revisited here — that's its own candidate, not a precedent to follow.
